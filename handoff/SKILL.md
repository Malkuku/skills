# Handoff

## 定位

Handoff 是由发送方工作区生成、交给零上下文接收方工作区执行的自包含跨边界任务单。

它用于跨工作区协同，不用于总结当前对话，也不用于同一工作区内恢复项目上下文。

默认假设接收方：

- 不知道发送方的 Spec、迭代任务、源码结构和历史对话；
- 无法访问发送方工作区中的文件；
- 只会根据 `HANDOFF.md` 和自身工作区内容完成任务；
- 需要明确知道外部契约如何变化、自己要改什么、必须保持什么以及如何验收。

发送方内部文档可以作为追溯来源，但不得代替正文说明。

## 使用边界

仅在当前工作区产生了另一个工作区必须承接的变化或任务时创建 Handoff，例如：

- 后端接口、字段、枚举或行为变化，需要前端同步；
- 前端提出新的请求或交互契约，需要后端实现；
- 设计原型已定稿，需要实际工程工作区落地；
- 部署、配置或运行方式变化，需要运维工作区调整；
- 公共数据模型、协议或共享组件变化，需要其他仓库同步。

以下情况不使用 Handoff：

- 变化完全封闭在当前工作区内部；
- 接收方不需要修改任何内容；
- 只是同一工作区内更换 agent 或恢复上下文；
- 已有共享 Spec、issue 或任务系统能够被双方直接访问，并且其中已经包含完整、可执行的跨工作区任务。

同一工作区的长期知识应写入 Spec、API、迭代任务或测试记录；Handoff 不替代这些正式工件。

## 输出位置

默认在当前工作区根目录创建或更新：

```text
HANDOFF.md
```

写入前先读取已有文件：

- 如果已有内容属于同一次交接，更新并补全；
- 如果已有内容已经完成或与当前交接无关，覆盖为新的交接任务；
- 不在同一个 `HANDOFF.md` 中混合多个互不相关的接收方任务。

如果需要同时交给多个工作区，应分别生成独立、面向各自接收方的 Handoff，避免让接收方自行筛选无关内容。

## 编写原则

### 面向接收方，而不是复述发送方

只写接收方完成任务所需的信息。

发送方内部可能修改了数据库、Mapper、Service、迁移脚本和测试，但如果跨边界影响只有 API 字段变化，Handoff 就只需要准确说明该字段变化及其对接收方的要求。

### 自包含

正文必须在无法访问发送方工作区的情况下仍然可执行。

不要只写：

```text
请按照 ITER-10 和后端 API Spec 同步修改。
```

应直接展开接收方需要的事实，例如：

```text
`PlanDTO` 新增 `repeatRule`：

- `frequency`: `daily | weekly | monthly`
- `repeatRule = null` 表示普通计划
```

### 描述外部影响，不复制实现过程

优先写：

- 对外字段、类型、枚举、接口或行为变化；
- 修改前与修改后的差异；
- 兼容方式和生效条件；
- 接收方需要完成的任务；
- 不得破坏的既有行为；
- 可独立验证的验收标准。

默认不写：

- 发送方完整迭代过程；
- 父子 agent 分工；
- 与接收方无关的源码文件列表；
- 发送方内部测试日志；
- 接收方无法访问且正文又依赖的路径引用；
- 无需接收方处理的内部改动。

### 不虚构接收方实现细节

发送方不了解接收方工作区时，只描述需要定位和修改的功能边界，不猜测具体文件、组件名或行号。

可以写：

```text
更新前端所有 `createTime` 的类型定义、字段引用和 mock 数据。
```

不要凭空写：

```text
修改 `src/views/document/List.vue` 第 82 行。
```

除非发送方确实读取过接收方工作区并确认该位置。

## 最小结构

```md
# Handoff

## 交接目标

- 来源工作区：
- 接收工作区：
- 任务主题：

## 背景

说明为什么接收方必须承接这次变化，只保留与接收方决策有关的背景。

## 契约或结果变化

使用明确的修改前 / 修改后、字段定义、示例数据、接口行为或交互结果说明变化。

## 接收方任务

列出接收方需要实际完成的修改。每项应可执行、可定位，不写空泛目标。

## 必须保持

列出不得破坏的兼容行为、既有规则、范围边界或明确禁止自行扩展的内容。

## 验收标准

列出接收方可以在自身工作区独立完成的验证结果。

## 发送方参考

可选。记录发送方用于追溯的 Spec、API、提交或任务路径；正文不得依赖这些路径才能理解。
```

## 内容要求

### 契约变化优先使用差异表达

字段、类型、枚举或行为变化时，优先提供：

- 修改前；
- 修改后；
- 删除或新增内容；
- 默认值和空值语义；
- 兼容期；
- 生效版本或部署顺序，若相关。

### 接收方任务必须可执行

任务应明确到接收方能在自己的工作区定位实现，例如：

- 更新类型定义；
- 替换旧字段引用；
- 调整请求参数；
- 更新 mock、fixture 或示例数据；
- 修改页面展示或错误映射；
- 补充对应验证。

不要只写“同步修改”“适配一下”“保持一致”。

### 验收标准只覆盖接收方责任

Handoff 的验收标准应验证接收方是否正确承接，不要求其重复验证发送方内部实现。

例如前端接收后端字段变化时，可以验证：

- 新字段能够正确解析和展示；
- 旧字段引用已移除；
- mock 与正式契约一致；
- 类型检查和相关前端测试通过。

不要求前端重新验证后端数据库迁移或后端单元测试。

## 与项目文档的关系

发送方在生成 Handoff 前，应先确保自身正式 Spec、API 或迭代任务已经记录本工作区内需要长期保留的事实。

Handoff 只导出跨工作区影响，不承担发送方项目记忆。

接收方完成任务后，应将稳定事实吸收到自身的 Spec、API、代码或测试中，然后删除 `HANDOFF.md`。

## 生命周期

```text
发送方产生跨边界变化
→ 在发送方根目录生成 HANDOFF.md
→ 用户将文件交给接收方工作区
→ 接收方 agent 读取并执行
→ 接收方将稳定结果写入自身正式工件
→ 验收完成后删除 HANDOFF.md
```

`HANDOFF.md` 是一次性交付物，不应长期作为项目事实来源，也不应在任务完成后继续保留造成重复执行。

## 完成前检查

- 接收方是否可以在完全不知道发送方上下文的情况下理解任务？
- 是否明确写出了跨边界变化，而不是只引用发送方内部文档？
- 是否包含接收方实际要完成的修改？
- 是否说明了必须保持的行为和范围边界？
- 验收标准是否能由接收方在自身工作区独立执行？
- 是否删除了与接收方无关的发送方实现过程？
- 是否避免虚构接收方的文件路径和实现细节？
- 是否只有一个明确的接收工作区和任务主题？
