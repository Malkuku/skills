# No Silent Shortcuts 中文版

## 核心规则

任何可能停止、跳过、取消、吞掉或延迟重要意图的短路，都不能是静默的。

这里的“意图”可以来自用户操作、API 请求、业务规则、后台任务、状态同步、表单提交、数据写入、队列消息或任意调用方的明确期待。

把这些分支当作一等决策处理，而不是顺手写下的普通 guard clause。

## 适用场景

当代码中出现会提前结束流程的分支时，先判断它是否会影响某个真实意图。

常见形式包括：

- `return`
- `continue`
- `break`
- 抛弃回调或事件
- 跳过 reducer/action/handler
- 取消请求、任务、事务或状态更新
- 将流程标记为完成、失败、取消、空闲或已处理

## 必须执行的做法

在新增或修改短路分支之前，先分类：

- 无害短路：纯内部 no-op，不会影响调用方期待，也不会改变业务结果。
- 关键短路：会阻止、跳过、取消、吞掉或延迟某个真实意图。

每个关键短路都必须在发生点留下可观测解释。根据项目习惯选择合适形式：

- 结构化日志
- 返回明确错误
- 抛出有语义的异常
- 写入诊断事件
- 更新可检查的状态
- 向调用方返回可区分的结果

解释至少回答：

- 为什么不能继续？
- 当前关键状态是什么？
- 期望状态是什么？
- 哪个输入、资源、条件或依赖不满足？
- 这个分支是否消费、保留、取消或忽略了原本的意图？

## 意图处理规则

任何将意图标记为已处理、已完成、已取消、已失败或无需执行的代码，都必须说明原因。

不要仅仅因为某个底层步骤返回了成功，就认为整体意图已经完成。

只有当该意图真正需要满足的业务条件已经成立时，才能消费或完成它。

最低诊断形态示例：

```ts
logger.debug("Skipping operation.", {
  reason,
  operationId,
  currentState,
  expectedState,
  consumedIntent: false
});
```

## 审查清单

完成前，检查自己的 diff 中是否有：

- `return;`
- `return undefined`
- `return null`
- `continue`
- `break`
- 空 `catch`
- 默认分支中的 no-op
- 清除、替换或取消待处理意图
- 状态转移到 `idle`、`done`、`error` 或 `cancelled`

逐项追问：

- 这会阻止某个调用方、用户或业务流程期待的结果吗？
- 用户、调用方或维护者是否需要知道它为什么发生？
- 原因是否能通过日志、诊断、事件或返回错误被观察到？
- 如果它消费了意图，完成条件是否明确？

如果答案不确定，就添加结构化诊断。

## 经验原则

静默短路会把调试成本从代码转移给使用者和维护者。关键分支必须在它决定不继续执行的那一刻解释自己。
