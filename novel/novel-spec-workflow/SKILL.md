# 小说 Spec 工作流

## 定位

把每部小说视为一个独立工作区。Spec 是小说工作区的一部分，用于保存作者已经形成的创作约束、当前有效设定、剧情规划和项目导航；正文是 Spec 之外的正式创作产物。

本 Skill 只定义长期工作方式，不保存某部小说的项目事实。具体人物、关系、世界、剧情和正文状态，以当前工作区内的 Spec、已确认正文和用户明确决定为准。

当工作区尚未初始化、关键 Spec 缺失，或既有小说首次接入本工作流时，读取 `references/project-onboarding.md`。

## 工作区边界

推荐的最小结构：

```text
小说工作区/
├─ Spec/
│  ├─ 索引.md
│  ├─ 核心创作说明.md
│  ├─ 设定/
│  └─ 大纲/
│     └─ 总体大纲.md
├─ 正文/
└─ GRILL_ME_DISCUSSION.md   # 仅在跨轮讨论时临时创建
```

按需增加：

- `Spec/创作任务/`：只用于跨文件、跨多轮、影响面较大或需要持续追踪的工作。
- `Spec/设定/` 下的文档或局部索引：由作品实际结构和对应领域 Skill 决定。
- `Spec/大纲/` 下的拆分文件：只有现有大纲过大或自然形成独立剧情范围时才创建。

不默认创建：

- 当前故事快照。
- 独立时间线或关键事件库。
- 固定的人物、关系、世界子目录。
- 完整废案库或文档内历史日志。
- 强制的大纲层级、节点生命周期或任务面板。

## Spec 内容职责

### 索引

`Spec/索引.md` 只承担两类信息：

- Spec 文档树：真实存在的正式 Spec、局部索引及其一句话用途。
- 极简当前进度指针：当前大纲位置、当前正文位置、当前创作状态和正在执行的独立任务入口。

索引不承担：

- Skill 触发或路由。
- 剧情摘要。
- 人物、关系或世界状态。
- 活跃线索、待办清单和维护日志。
- 其他 Spec 内容的重复副本。

索引不是固定读取入口。执行任务时，根据当前请求判断所需事实；已知文档位置时可直接读取，不确定位置或需要了解文档结构时再使用索引。

新增、删除、移动、重命名正式 Spec 或局部索引后，同步维护文档树。不要登记不存在的文档，也不要把全部物理目录机械复制进索引。

### 核心创作说明

`Spec/核心创作说明.md` 只保存作者层面的长期约束：

- 期望读者获得的体验。
- 作品整体基调。
- 作者明确的创作边界。

故事前提、人物处境、世界观、核心矛盾、主线剧情和结局方向进入总体大纲或对应设定，不写入核心创作说明。

普通大纲、正文、润色和审查任务默认只读核心创作说明。只有用户明确改变作品体验、基调或边界时才修改。

### 设定

`Spec/设定/` 保存当前有效的故事设定。它可以随剧情发展动态变化。

核心工作流不规定设定目录的内部分类和文档模板。人物、人际关系、世界、地点、组织、能力体系或其他内容如何组织，由作品需要和对应领域 Skill 决定。

维护原则：

- 人物变化回到人物所属设定。
- 关系变化回到对应关系设定。
- 世界、组织、地点或物品变化回到对应设定。
- 不为人物状态、关系状态或世界状态另建重复事实源。
- 设定文档以当前已经成立、当前仍有效的内容为主。
- 未来计划原则上写入大纲；必要的发展设计可以引用，但必须与当前事实明确区分。

### 大纲

`Spec/大纲/` 保存故事构想和具体剧情规划。大纲首先描述故事准备发生什么，是故事主脉络，不用抽象目标替代具体事件。

大纲可以同时包含：

- `候选`：已经进入正式大纲，但仍可讨论、替换或扩充。
- `已确认`：已经形成共识，可以作为正文创作依据。

只保留这两类最小状态。正文写作和修订进度由正文与索引中的进度指针体现，不为大纲建立复杂生命周期。

大纲的组织边界由创作者自然决定：

- 优先在现有文件中继续扩充和修订。
- 不预设“总体—分卷—节点—章节—场景”的强制层级。
- 当一份大纲因篇幅、主题跨度或维护成本过大时，再按卷、篇章、阶段或自然剧情范围拆分。
- 拆分后避免同一剧情在多个文件中重复保存，并同步维护索引与必要链接。

大纲是否合理，需要结合人物动机、人物认知、因果关系、世界条件和前后剧情进行审查。审查结论可以直接写入相关大纲段落、候选方案或讨论草稿，不强制每个剧情段套用固定表格。

### 正文

正文位于 Spec 之外，承担完整事件、对白、表现和叙事细节。

正文状态至少区分：

- 尚未确认的草稿或修订稿。
- 已被用户明确确认，或按项目约定进入有效正文链的正文。

只有已确认正文才能形成正式故事事实，并触发对应设定、大纲和索引的维护。草稿可以产生影响分析和候选变更，但不能自动改写当前有效 Spec。

正文能够承担一般事件记录。不要再为每章建立章节事件库，也不单独维护完整时间线。事件造成的长期变化进入对应设定；事件在整体剧情中的位置和承接由大纲与正文承担。

### 独立创作任务

普通的人设设计、大纲扩充、正文写作、局部润色和单点审查直接执行，不创建任务文档。

仅在以下情况按需创建 `Spec/创作任务/`：

- 工作跨多个 Spec 或正文文件。
- 预计跨多轮持续推进。
- 涉及大范围设定替换、全卷修订或系统性审查。
- 需要明确记录范围、影响、未完成事项和后续入口。

任务文档只服务当前复杂工作。完成后将长期事实迁移到正式设定、大纲或索引；没有继续保留价值时删除或归档，不让任务记录成为第二套项目事实。

## 事实解释权

不建立“正文大于设定大于大纲”一类机械总优先级。根据问题类型判断依据：

- 作者体验、基调和边界：以 `核心创作说明` 为准。
- 当前有效的人物、关系、世界及其他状态：以对应设定为操作性事实源。
- 未来准备发生的剧情：以大纲为准，并区分候选与已确认。
- 正式故事实际写出了什么：以已确认正文为原始证据。
- 项目当前写到哪里：以索引中的极简进度指针和正文实际文件为准。

发生不一致时，先分类，不静默覆盖：

- 正文执行偏差：正文没有合理依据地违背已确认设计，优先修正文或标记待重写。
- Spec 漂移：已确认正文形成了合理的新事实，但对应设定、大纲或索引尚未同步，维护 Spec。
- 创作方向变更：新发展会改变重要人物逻辑、主线或创作边界，交给 `grill-me` 讨论。
- 导航或摘要错误：索引、链接或任务入口不准确，直接修正确定性内容。

## 动态维护

### 读取原则

根据当前请求判断需要哪些项目事实，读取必要的 Spec、正文和讨论材料。不要为了流程完整机械扫描整个工作区，也不要把本可从文档确认的事实再次询问用户。

修改重要设定前：

1. 读取该设定及文档中的强关联。
2. 对旧事实、关键表达或相关对象执行定向检索。
3. 判断受影响的大纲、正文和其他设定。

重要文档可以保存少量强关联和必要来源，但不维护完整依赖图，也不追求列出所有提及。

### 变化分级

领域 Skill 可以直接维护正式 Spec，但必须区分变化性质：

- 确定性更新：路径、链接、索引、进度指针、已明确的引用等，直接更新。
- 已确认创作决定：用户已经确认的设定或剧情变化，写入对应正式 Spec。
- AI 候选变化：由推演、写作或审查产生但尚未确认的内容，只保留为候选、讨论项或任务记录。
- 冲突或高影响变化：会改变核心边界、重要人物逻辑、主线剧情，或与现有事实明显冲突，交给 `grill-me`。

不得把 AI 的合理推断包装成用户已经确认的事实。

### 任务收口

讨论、推演或草稿阶段不持续污染正式 Spec。候选内容保留在大纲的候选部分、当前任务或 `GRILL_ME_DISCUSSION.md` 中。

形成稳定结果后，把本次工作视为一次维护事务：

1. 确认最终采用的正文、设定或剧情方案。
2. 判断它改变了哪些当前有效内容。
3. 按事实归属更新对应设定。
4. 更新相关大纲内容和候选/已确认标记。
5. 更新索引中的文档树和极简进度指针。
6. 检查受影响内容是否需要直接修正、标记复审或进入讨论。
7. 清理已被正式 Spec 承接的临时讨论与迁移说明。

收口时不要求机械输出固定报告，但必须让用户清楚：正式采用了什么、更新了哪些项目事实、哪些仍是候选或未解决问题。

## 当前版本与历史

正式 Spec 默认只保存当前有效版本：

- 修改时直接维护当前内容，不长期堆积删除线、旧版段落和废案。
- 普通历史由 Git 承担。
- 不建立完整废案库或每份文档内部的变更日志。

只有旧内容仍影响当前大纲、已确认正文或其他设定时，才保留临时迁移说明。迁移说明必须列出尚未处理的具体影响和清理条件；影响处理完成后删除。

## 与 Grill Me 的协作

以下情况进入 `grill-me`：

- 用户希望共同构思、压力测试或比较剧情、人设与设定方案。
- 候选之间存在会显著改变故事结果的分支。
- 正文自然发展与已有大纲或设定冲突，无法仅凭现有证据判断应修改哪一侧。
- 变化会影响核心创作说明、重要人物逻辑或主线方向。

`GRILL_ME_DISCUSSION.md` 只是临时讨论容器。稳定结论形成后迁移到对应正式 Spec；正式工件已经承接必要内容后删除草稿。

不要为了显得严谨继续询问已不影响整体架构、可以在实践中自然调整或能够从现有材料判断的细节。

## 完成前检查

- 是否读取了本次任务真正需要的项目事实，而不是无目的扫描。
- 是否区分了当前有效设定、未来大纲、候选方案和已确认正文。
- 是否把变化更新到其所属设定，而不是创建重复状态文档。
- 是否只让已确认正文形成正式故事事实。
- 是否按变化等级直接更新、保留候选或进入讨论。
- 是否在任务收口时同步维护相关设定、大纲、索引和正文入口。
- 是否只保留当前有效 Spec，并清理已完成的临时迁移说明或讨论草稿。
- 是否避免把显然可自行判断的操作细节继续抛给用户。
