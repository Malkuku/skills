# Page Prototype Design Notes

## 页面角色

先判断页面职责：

- 工作台：帮助用户判断下一步并直接操作。
- 列表页：浏览、筛选、批量处理和进入详情。
- 详情页：承载完整字段、编辑和状态流转。
- 统计页：解释趋势、分布、异常和可追问的问题。
- 输入页：减少干扰，突出保存、提交和失败恢复。
- 聊天页：承载对话上下文、生成动作和引用结果。

不要把所有职责塞进一个页面。首页或 Dashboard 通常只做摘要、下一步和轻量操作。

## 首屏问题

每个页面先回答一个主问题：

- 今天先做什么？
- 当前哪里出问题？
- 哪些内容需要我处理？
- 我要输入什么，保存到哪里？
- 我如何进入完整详情？

如果一个区域不能支持主问题，就删除、降级或移到其他页面。

## 信息层级

优先使用结构表达层级，其次才是颜色和文案。

- 主结构：列、行、时间轴、分组、工作区。
- 次结构：卡片、任务块、状态栏、分隔线。
- 轻提示：chip、颜色、短标签。
- 最后才是解释文本。

不要用图例或规则面板解释本应由布局表达的关系。

## 任务工作台

任务类 Dashboard 必须考虑：

- 时间范围：当前页面看到的是今日、本周、全部还是筛选结果。
- 任务优先级：使用业务契约已有优先级，不自行发明等级命名。
- 截止约束：哪些必须在今日完成，哪些只是本周重要。
- 直接动作：完成、取消/跳过、打开详情。
- 密度控制：任务项保留标题、时间/范围、优先级、必要状态和轻量动作。

在设计任务详情、抽屉或编辑区前，先核对数据契约：

- 契约内字段：可以作为可编辑表单字段或保存动作，例如标题、备注、标签、优先级、日期、状态、清单等。
- 前端派生展示：可以展示但不应伪装成可保存字段，例如当前时间范围、剩余时间、今日必完、任务块位置和排序说明。
- 待契约能力：没有 API 或数据库字段时，必须显式标注为待契约，不进入正式表单，例如完成备注、取消原因、检查清单、操作日志等。若 API 已定义 `startAt/endAt` 这类分钟级时间字段，则可以进入原型表单和时间轴。

不要为了让抽屉或详情区显得“占位够多”而添加未定义字段。空间可以大，但内容必须先贴合已有契约；需要新增能力时，先提出 API/数据契约变更，而不是在原型里悄悄混入。

时间轴可以表达截止时间或工作窗口，但不要混淆二者。若用时间做竖轴，任务可沿横轴累计；标题较长或空间不足时允许块状任务向竖向堆叠，但必须保持截止线和完成/取消入口清晰。

Dashboard 中高频任务操作优先使用就地抽屉，不默认跳转到详情页：

- 任务块点击选中任务并展开抽屉，主时间轴位置不丢失。
- 任务块内保留完成、取消等轻量动作。
- 抽屉承载选中任务的上下文操作，优先使用契约内字段；缺失契约的操作必须标明待契约或移出表单。
- 当抽屉承载核心工作流时，应表现为真正从边缘展开的重点操作区，保留足够宽度和高度，而不是普通右栏卡片。
- 完整复杂编辑可以保留在详情页，但 Dashboard 的常用工作流应能在抽屉闭环。

## 交互语义

- 看起来像按钮的元素必须可点击；否则改成 badge、文本或状态标识。
- “今日”“本周”等时间范围如果只是当前视图状态，不应做成普通按钮。
- AI 摘要、建议、规则说明等内容只有在用户会据此行动时才放入核心区域。
- 页面原型中的静态时间可写死，但应对应正式实现的动态当前日期时间。

## 验证口径

静态原型优先做人工审查：

- 首屏是否能回答页面主问题。
- 每个区域是否有用户价值。
- 关键动作是否可见。
- 重要与不重要是否一眼能区分。
- 移动端是否不会重叠、截断或误导。

只有进入正式源码、构建链路或集成行为时，才默认运行构建或测试。
