# Spec 驱动 Agent 工作流

## 定位

把仓库视为由分层 Spec 驱动的长期工程。先理解产品意图、架构契约和任务边界，再决定是否讨论、直接修改、拆分迭代或维护文档。

本 skill 只定义工作流，不保存项目事实。具体产品、架构、模块 API 和当前迭代状态以仓库内 Spec 为准。

## Spec 分层

- `Me2AI`：产品侧设计、理念、UI/交互方向，默认只读。
- `AI2AI`：Agent 侧架构记忆、模块契约、迭代任务和测试策略，需要随工程演进维护。
- `AI2AI/索引`：入口文档。查代码前优先通过索引定位相关架构/API/迭代文档。
- `AI2AI/API`：模块外部契约。跨模块调用、接口、数据模型、消息协议、事件协议和持久化边界优先查这里。
- 源码：实现事实。只有 Spec/API 不足，或需要修改/验证时，再进入 CodeBase。

仓库初始化、空 Spec、缺少 Me2AI/AI2AI，或既有项目引入该流程时，读取 `references/project-onboarding.md`。

## 请求分类

处理前先分类：

- 讨论/规划：询问方案、规则、架构、流程、风险或评估想法。只读必要 Spec 并给建议，除非用户明确要求改文件。
- 细节任务：单一问题，边界清楚，只影响少量文件，不改变核心架构、跨模块 API、入口、持久化或协议。当前 Agent 可直接执行。
- 迭代任务：涉及多个模块、产品入口、架构/API、持久化、消息协议、测试方案、验收材料或文档体系。按父 Agent 协调流程执行。
- 任务清单：多个编号项、目标或路线图。先逐项判断独立性、类型、依赖和文档需求，再建议拆分或合并。

分类不确定时，说明判断依据和推荐边界，不直接开工。

## 执行规则

- 索引优先，契约优先，必要时再读源码。
- Me2AI 默认只读；AI2AI 随架构、API、测试和迭代事实维护。
- 外部契约变化时，同步更新对应 AI2AI/API 文档。
- 代码修改后运行相关测试；有代码修改时至少运行项目要求的构建验证。
- 发现细节任务扩大为跨模块/API/协议/持久化变化时，停止直接实现，重新按迭代任务判断。

## 迭代任务

父 Agent 负责协调，不独自完成主要实现。

如果迭代任务文档显式声明了 Agent 分工，该分工是强制完成门禁，优先于默认子 Agent 拆分规则。

- 父 Agent 不得自行替代已声明的设计、实现、测试、验收或其他交付角色。
- 每个已声明 Agent 角色必须产生可审阅交付物，例如设计结论、实现变更、测试计划、测试报告、审查结论或明确阻塞记录。
- 缺少任一已声明角色交付物时，迭代状态不得标为 `已完成`；只能标为 `进行中`、`实现完成待测试`、`验收待补测` 或项目已有等价状态。
- 如果父 Agent 认为既有分工不适合当前任务，必须先说明原因，并获得用户确认或更新迭代任务文档后再执行；不得用“任务集中”“串行更稳”“避免机械拆分”等理由自行取消已声明角色。
- 事后补派 Agent 只能作为纠偏记录，不等同于原流程合规；父 Agent 收口时必须如实记录流程偏差和剩余风险。

索引状态维护：

- `AI2AI/索引` 的迭代任务入口必须包含每个任务的状态和当前迭代进度，避免后续 Agent 反复扫描任务正文。
- 初始化阅读索引时，如发现迭代任务列表缺少状态，应先根据各任务文档的完成记录补齐索引，再继续判断当前任务。
- 创建迭代任务文档时，同步在索引登记任务，状态标为 `待开始` 或项目已有等价状态。
- 创建带 Agent 分工的迭代任务文档时，必须在任务文档中明确说明该分工是完成门禁，父 Agent 不得自行替代各角色执行；缺少任一角色交付物时不得标记为已完成。
- 开始实现或协调实现时，同步把索引状态标为 `进行中`。
- 任务完成后，必须同时填写任务文档完成记录，并把索引状态改为 `已完成`，更新当前迭代进度说明。

基本顺序：

1. 阅读必要 Spec、索引、API 和架构文档。
2. 判断任务边界、依赖、风险和验收口径。
3. 创建或安排子 Agent 创建迭代任务文档；安排前先按“子 Agent 拆分规则”判断是否真的需要委派。
4. 父 Agent 审阅范围、设计决策、验收标准、测试计划和文档更新项。
5. 审阅通过后，再创建必要的实现/测试 Agent；实现任务必须引用迭代任务文档。
6. 实现后安排测试、构建验证、文档维护和完成记录。
7. 父 Agent 审阅整合结果。
8. 按项目要求提交 git；迭代 commit 使用中文描述。

子 Agent 拆分规则：

- 子 Agent 不是检查清单。请求参数、DTO、Service、Persistence、Controller、排序规则、错误码等关注点，默认写入同一个设计/实现 Agent 的检查项，除非它们具备独立交付物和独立验收口径。
- 只有同时满足以下条件时才拆出子 Agent：任务边界清楚；可独立提交或独立产出文档/测试/代码；不需要与其他 Agent 共同修改同一核心文件；结果可由父 Agent 单独验收。
- 单接口或单领域闭环迭代默认不超过三段：设计+实现 Agent、测试 Agent、父 Agent 审阅收口。确需更多 Agent 时，必须在任务文档中说明每个 Agent 的独立交付物和拆分收益。
- 父 Agent 审阅收口是流程职责，不算实现子 Agent；不要把 Review/Documentation 机械拆成独立 Agent，除非文档收口本身是主要交付物或跨多个已完成迭代。
- 共享 API、数据模型、持久化、核心 Service 或同一 Controller 的工作应优先串行并收敛到同一实现 Agent，避免口径漂移和重复整合。
- 并行 Agent 只用于互不冲突且能减少总耗时的工作。若并行带来的上下文同步成本高于实现成本，应合并。

硬性约束：

- 不得把任务文档创建和主要代码实现并行。
- 不得在父 Agent 审阅迭代任务文档前启动实现。
- 存在 API、数据模型、消息协议、持久化或核心文件依赖的任务必须串行。
- 多个任务只有边界清楚且互不冲突时才可并行。

## 任务清单

对每项标注：

- 是否独立。
- 是讨论、细节任务还是迭代任务。
- 是否依赖其他项。
- 是否涉及 API、数据模型、协议、持久化、测试方案或文档结构。
- 是否需要迭代任务文档或 AI2AI/API 更新。

只有在多项必须同时验收、共享同一架构变更，或用户明确要求时才合并。否则优先拆分。

## 完成前检查

- 请求类型是否判断正确。
- 是否读过必要 Spec/API。
- 是否保持 Me2AI 只读、AI2AI 可维护。
- 是否避免未确认的大范围合并。
- 代码修改后是否完成构建验证。
- 契约或测试范围变化时，是否同步维护 AI2AI。
- 迭代任务是否有任务文档、完成记录和中文 git commit。
- `AI2AI/索引` 是否记录最新迭代任务状态和当前迭代进度。
