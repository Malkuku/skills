# Spec 驱动 Agent 工作流

## 定位

把仓库视为由分层 Spec 驱动的长期工程。先理解产品意图、架构契约和任务边界，再决定讨论、直接修改、拆分迭代或维护文档。

本 skill 只定义工作流，不保存项目事实。具体产品、架构、模块 API、文档结构和当前迭代状态，以仓库内 Spec 与实现证据为准。

## Spec 分层与事实边界

- `Me2AI`：产品意图、用户价值、功能设计和 UI/交互方向，默认只读。
- `AI2AI`：Agent 侧工程记忆，包括总体架构、模块契约、测试策略、文档索引和迭代任务，需要随工程演进维护。
- `AI2AI/API`：模块外部契约。跨模块调用、接口、数据模型、消息/事件协议和持久化边界优先查这里。
- CodeBase：当前实现事实。只有 Spec/API 不足，或需要修改、定位、验证时，再进入源码。
- Tests、构建和运行结果：实现是否满足契约的验证证据。

发生冲突时，不笼统宣称某一层永远正确：

- 讨论产品目标时，以 `Me2AI` 为意图依据。
- 判断外部契约时，以 `AI2AI/API` 为规范依据。
- 判断当前实际行为时，以 CodeBase 和验证结果为事实依据。
- Spec 与实现不一致时，明确标记为实现偏差或 Spec 漂移，不自行抹平差异。

仓库初始化、空 Spec、缺少 Me2AI/AI2AI，或既有项目引入该流程时，读取 `references/project-onboarding.md`。

## 索引与 Spec 文档树

`AI2AI/索引` 是查代码前的首要导航入口。它不只维护当前迭代，还必须呈现项目的 Spec 文档树骨架。

文档树按以下层级维护：

- 根索引展开到稳定主题、领域或局部索引。
- 局部索引展开到可直接选择的具体文档。
- 单份文档内部的章节由文档自身目录负责，不进入项目文档树。
- 每一层只展开到足以判断“下一步应该读取哪个文档或子索引”为止。

根索引中的 `Spec 文档树` 推荐使用浅树状结构，而不是按物理文件树全量展开。初始化时优先采用以下形态，并只登记已经存在或本次创建的文档：

```text
- Me2AI
  - [核心项目说明](../Me2AI/核心项目说明.md)：产品意图、用户价值与业务边界。
- AI2AI
  - [技术选型与总体架构](./技术选型与总体架构.md)：技术栈、运行模型、模块边界。
  - [测试方案](./测试方案.md)：验证入口、测试缺口、最小充分验证策略。
  - API
    - [API 索引](./API/README.md)：外部接口、远程模块、领域 API 文档入口。
  - 迭代任务
    - [迭代任务模板](./迭代任务/模板.md)：后续任务文档格式。
```

如果某一分支会继续扩展，例如 `API`、`迭代任务`、`验收材料` 或 `领域文档`，根索引只指向该分支的局部索引；局部索引再展开具体文档。不要把所有模块 API、任务历史或源码目录直接塞进根索引。

避免机械追求固定层数。通常根索引不超过“分层 → 主题/领域 → 文档或局部索引”三层；某分支直接子项超过约 7～10 个，或名称不足以支持读取决策时，应建立局部索引，而不是继续在根索引平铺。

文档树应忠实反映实际 Spec，不得为了完整性登记不存在的文档。节点只保留路径或链接、清晰名称和必要的一句话用途；不要把完整依赖、代码清单、历史细节和大段元数据堆入根索引。

出现以下变化时同步维护文档树：

- 新增、删除、移动或重命名 Spec 文档或局部索引。
- 新增稳定模块、API 契约、测试入口或文档分区。
- 某区域从“待梳理”转为稳定文档，或文档权威关系发生变化。
- 当前迭代、阻塞任务和近期待开始任务发生变化。

迭代任务分支只在根索引展示当前进行中、待开始、阻塞任务和当前进度；完整历史任务进入局部索引，避免根索引持续膨胀。

## 请求分类

处理前先分类：

- 讨论/规划：询问方案、规则、架构、流程、风险或评估想法。只读必要 Spec 并给建议，除非用户明确要求改文件。
- 细节任务：单一问题，边界清楚，只影响少量文件，不改变核心架构、跨模块 API、入口、持久化或协议。当前 Agent 可直接执行。
- 迭代任务：涉及多个模块、产品入口、架构/API、持久化、消息协议、测试方案、验收材料或文档体系。按父 Agent 协调流程执行。
- 任务清单：多个编号项、目标或路线图。先逐项判断独立性、类型、依赖和文档需求，再建议拆分或合并。

分类不确定时，说明判断依据和推荐边界，不直接扩大范围开工。

## 通用执行规则

- 索引优先，契约优先，必要时再读源码。
- Me2AI 默认只读；AI2AI 随架构、API、测试、文档树和迭代事实维护。
- 外部契约变化时，同步更新对应 AI2AI/API 文档。
- 验证遵循“最小充分范围”，根据影响面选择验证，不把全套测试作为任何代码修改的默认动作。
- 发现细节任务扩大为跨模块/API/协议/持久化变化时，停止直接实现，重新按迭代任务判断。

## 最小充分验证

任务文档或执行计划必须说明受影响范围、正式验证项和明确不需要执行的高成本验证。默认按以下边界判断：

- 文档、注释、纯展示文案：检查格式、链接和结构；除非影响生成流程、配置或构建输入，否则不运行构建。
- 单文件或局部实现、无契约变化：运行定向测试、静态检查或受影响模块的最小编译验证。
- 单模块逻辑变化：运行相关模块测试和模块构建。
- 跨模块、API、数据模型变化：运行受影响模块构建，以及必要的契约或集成测试。
- 持久化、协议、基础设施、发布或核心架构变化：运行相关迁移、启动、集成或发布验证；只有影响范围广、项目明确要求或风险无法局部覆盖时才运行全套测试。

有独立测试 Agent 时：

- 实现 Agent 可以运行支持开发的快速自查，但不得把自查当作正式验收结论。
- 测试 Agent 按约定范围执行正式验证并提交证据。
- 父 Agent 审阅测试证据，不重复执行同一套测试或构建。

没有独立测试 Agent 的细节任务，由当前 Agent 按最小充分范围完成验证；不得因为缺少测试 Agent 自动升级为全套测试。

## 迭代任务

父 Agent 负责协调、门禁和收口，不独自完成主要实现。

### 任务文档与用户可见摘要

迭代任务文档是 Agent 协作契约，不要求用户直接阅读全文。

任务文档创建并经父 Agent 内部审阅后，父 Agent 必须在对话中向用户交付一份简短的执行摘要，至少包含：

- 对目标的理解。
- 关键方案和重要边界。
- 明确不做或暂不处理的内容。
- 预期交付物。
- 真实存在的用户决策项；没有则明确无须用户额外审批。

用户目标明确、方案没有重大分叉且用户已要求执行时，交付摘要后可继续推进，不得机械等待用户回复。只有存在会显著改变结果的歧义、范围扩大、不可逆操作、兼容性破坏、核心产品/架构分叉，或与用户既有决定冲突时，才进入 `待关键决策` 并暂停相关实现。

不得只在仓库中创建任务文档而不向用户说明 Agent 将如何执行；也不得把审阅整份内部任务文档的责任转交给用户。

### Agent 分工与权限边界

如果迭代任务文档显式声明了 Agent 分工，该分工是强制完成门禁，优先于默认拆分规则。

- 父 Agent 不得自行替代已声明的设计、实现、测试、验收或其他交付角色。
- 每个已声明角色必须产生可审阅交付物，例如设计结论、实现变更、测试报告、审查结论或明确阻塞记录。
- 缺少任一已声明角色交付物时，迭代状态不得标为 `已完成`；只能标为 `进行中`、`实现完成待测试`、`测试完成待收口`、`验收待补测` 或项目已有等价状态。
- 如果父 Agent 认为既有分工不适合当前任务，必须先说明原因，并获得用户确认或更新迭代任务文档后再执行；不得自行取消已声明角色。
- 事后补派 Agent 只能作为纠偏记录，不等同于原流程合规；收口时必须如实记录流程偏差和剩余风险。

父 Agent 的收口职责是审阅交付物和证据，而不是重新执行子 Agent 的工作：

- 可以检查测试报告是否覆盖验收标准，命令、环境、结果和失败记录是否完整，以及测试后是否又发生变更。
- 发现覆盖不足时，应退回原测试 Agent 补测或重新指派必要范围的测试，不应由父 Agent 自己补做。
- 测试完成后没有相关变更时，不得为了“更保险”重复运行相同测试、构建或手动验收。
- 只有测试后代码/配置/依赖/脚本发生变化，证据矛盾或缺失且原角色无法补充，出现新的高风险问题，或用户/项目明确要求独立复验时，才允许重新验证；必须记录原因并限制到受影响范围。
- 父 Agent 在收口时修改了实现，相关测试证据立即失效，必须重新交由测试角色验证受影响范围。

### 索引状态维护

- `AI2AI/索引` 的迭代入口必须记录当前任务状态和当前迭代进度，避免后续 Agent 反复扫描任务正文。
- 初始化阅读索引时，如发现任务状态缺失或与任务文档完成记录冲突，应先修正索引，再判断当前任务。
- 创建迭代任务文档时，同步在索引登记任务，状态标为 `待开始` 或项目已有等价状态。
- 存在必须由用户判断的关键问题时，状态标为 `待关键决策`；没有真实决策项时不得滥用该状态。
- 开始实现或协调实现时，把状态标为 `进行中`。
- 实现、测试和收口阶段按项目状态体系更新，不得在缺少正式交付物或验证证据时提前标记完成。
- 任务完成后，同时填写任务文档完成记录、更新索引状态和当前迭代进度；若新增或移动了 Spec，也同步维护文档树。

### 基本顺序

1. 读取根索引和必要的局部索引、Spec、API 与架构文档。
2. 判断任务边界、依赖、风险、验收口径和最小充分验证范围。
3. 创建或安排子 Agent 创建迭代任务文档；安排前先判断是否真的需要委派。
4. 父 Agent 审阅范围、设计决策、Agent 分工、验收标准、测试范围和文档更新项。
5. 向用户交付执行摘要；仅在存在真实关键决策时暂停等待。
6. 审阅通过后，再创建必要的实现/测试 Agent；实现任务必须引用迭代任务文档。
7. 实现后由约定测试角色完成正式验证，随后维护文档和完成记录。
8. 父 Agent 审阅交付物与验证证据，处理阻塞或退回补充，不重复角色工作。
9. 更新索引中的文档树、任务状态和当前进度。
10. 按项目要求提交 git；迭代 commit 使用中文描述。

### 子 Agent 拆分规则

- 子 Agent 不是检查清单。请求参数、DTO、Service、Persistence、Controller、排序规则和错误码等关注点，默认写入同一个设计/实现 Agent 的检查项，除非具备独立交付物和独立验收口径。
- 只有同时满足以下条件时才拆出子 Agent：任务边界清楚；可独立提交或产出文档/测试/代码；不需要与其他 Agent 共同修改同一核心文件；结果可由父 Agent 单独验收。
- 单接口或单领域闭环迭代默认不超过三段：设计+实现 Agent、测试 Agent、父 Agent 审阅收口。确需更多角色时，必须在任务文档中说明独立交付物和拆分收益。
- 父 Agent 审阅收口是流程职责，不算实现子 Agent；不要把 Review/Documentation 机械拆成独立 Agent，除非文档收口本身是主要交付物。
- 共享 API、数据模型、持久化、核心 Service 或同一 Controller 的工作应优先串行并收敛到同一实现 Agent，避免口径漂移和重复整合。
- 并行 Agent 只用于互不冲突且能减少总耗时的工作。若上下文同步和整合成本高于实现成本，应合并。

### 硬性约束

- 不得把任务文档创建和主要代码实现并行。
- 不得在父 Agent 审阅任务文档、确定执行摘要和验证范围前启动实现。
- 存在 API、数据模型、消息协议、持久化或核心文件依赖的任务必须串行。
- 多个任务只有边界清楚且互不冲突时才可并行。
- 父 Agent 不得以收口、保险或复核为名重复测试 Agent 已完成且仍有效的正式验证。

## 任务清单

对每项标注：

- 是否独立。
- 是讨论、细节任务还是迭代任务。
- 是否依赖其他项。
- 是否涉及 API、数据模型、协议、持久化、测试方案或文档结构。
- 是否需要迭代任务文档、AI2AI/API 更新或文档树更新。

只有在多项必须同时验收、共享同一架构变更，或用户明确要求时才合并。否则优先拆分。

## 完成前检查

- 请求类型是否判断正确。
- 是否通过根索引和局部索引读取了必要 Spec/API，避免无目的扫描。
- 是否保持 Me2AI 只读、AI2AI 可维护，并正确处理 Spec 与实现冲突。
- 迭代任务是否已向用户交付执行摘要，而不是只创建内部文档。
- 是否只在存在真实关键决策时暂停用户审批。
- Agent 分工是否得到遵守，父 Agent 是否避免越权和重复执行。
- 验证是否符合最小充分范围；全套测试是否有明确必要性。
- 契约、测试范围或文档结构变化时，是否同步维护 AI2AI。
- 迭代任务是否有任务文档、完成记录、有效验证证据和项目要求的 git commit。
- `AI2AI/索引` 是否记录最新 Spec 文档树、当前任务状态和当前迭代进度。
