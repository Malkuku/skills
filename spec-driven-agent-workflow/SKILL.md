# Spec 驱动 Agent 工作流

## 定位

把仓库视为由分层 Spec 驱动的长期工程。先理解产品意图、架构契约和任务边界，再决定讨论、直接修改、拆分迭代或维护文档。

本 skill 只定义工作流，不保存项目事实。具体产品、架构、模块 API、文档结构和当前迭代状态，以仓库内 Spec、实现和验证证据为准。

## 事实层级

- `Me2AI`：产品意图、用户价值、功能设计和 UI/交互方向，默认只读。
- `AI2AI`：Agent 工程记忆，包括总体架构、模块契约、测试策略、文档索引和迭代任务，需要随工程演进维护。
- `AI2AI/API`：模块外部契约。跨模块调用、接口、数据模型、消息/事件协议和持久化边界优先查这里。
- CodeBase：当前实现事实。只有 Spec/API 不足，或需要定位、修改、验证时，再进入源码。
- Tests、构建和运行结果：实现是否满足契约的验证证据。

发生冲突时按问题类型判断：

- 产品目标 → `Me2AI`。
- 外部契约 → `AI2AI/API`。
- 当前实际行为 → CodeBase 和验证结果。
- Spec 与实现不一致 → 明确标记实现偏差或 Spec 漂移，不自行抹平。

仓库初始化、空 Spec、缺少 Me2AI/AI2AI，或既有项目首次引入该流程时，读取 `references/project-onboarding.md`。

## 索引与文档树

`AI2AI/索引` 是查代码前的首要导航入口，同时维护项目 Spec 文档树、当前任务状态和当前迭代进度。

文档树遵循：

- 根索引展开到稳定主题、领域或局部索引。
- 局部索引展开到可直接选择的具体文档。
- 单份文档内部章节由文档自身目录负责，不进入项目文档树。
- 每层只展开到足以判断“下一步该读哪个文档或子索引”为止。
- 不机械追求固定层数；通常根索引不超过“分层 → 主题/领域 → 文档或局部索引”三层。
- 某分支直接子项超过约 7～10 个，或名称不足以支持读取决策时，建立局部索引。
- 根索引只保留路径/链接、清晰名称和必要的一句话用途，不堆完整依赖、源码清单和历史细节。
- 只登记真实存在或本次创建的文档，不为完整性虚构节点。
- 迭代任务分支只在根索引展示当前进行中、待开始、阻塞任务和当前进度；完整历史进入局部索引。

初始化时可采用类似结构，并只登记实际存在的文档：

```text
- Me2AI
  - [核心项目说明](../Me2AI/核心项目说明.md)：产品意图、用户价值与业务边界。

- AI2AI
  - [技术选型与总体架构](./技术选型与总体架构.md)：技术栈、运行模型、模块边界。
  - [测试方案](./测试方案.md)：验证入口、测试缺口、最小充分验证策略。
  - API
    - [API 索引](./API/README.md)：外部接口、远程模块、领域 API 文档入口。
  - 迭代任务
    - [迭代任务模板](./迭代任务/模板.md)：后续任务文档格式。
````

出现以下变化时同步维护索引和文档树：

* 新增、删除、移动或重命名 Spec 文档或局部索引。
* 新增稳定模块、API 契约、测试入口或文档分区。
* 某区域从待梳理转为稳定文档，或文档权威关系变化。
* 当前迭代、阻塞任务和近期待开始任务变化。

初始化读取索引时，如发现任务状态缺失或与任务文档完成记录冲突，应先修正索引，再判断当前任务。

## 请求分类

处理前先分类。

### 讨论/规划

询问方案、规则、架构、流程、风险或评估想法。

只读必要 Spec 并给建议；除非用户明确要求，否则不修改文件。

### 细节任务

单一问题，边界清楚，只影响少量文件，不改变核心架构、跨模块 API、入口、持久化或协议。

当前 Agent 可直接执行。

如果执行过程中发现范围扩大到跨模块/API/协议/持久化或核心架构变化，停止按细节任务继续，重新分类为迭代任务。

### 迭代任务

涉及多个模块、产品入口、架构/API、持久化、消息协议、测试方案、验收材料或文档体系。

按父 Agent 协调流程执行。

### 任务清单

多个编号项、目标或路线图时，逐项判断：

* 是否独立。
* 属于讨论、细节任务还是迭代任务。
* 是否依赖其他项。
* 是否涉及 API、数据模型、协议、持久化、测试方案或文档结构。
* 是否需要迭代任务文档、`AI2AI/API` 更新或文档树更新。

只有多项必须共同验收、共享同一核心架构变更，或用户明确要求时才合并；否则优先拆分。

分类不确定时，说明判断依据和推荐边界，不直接扩大范围开工。

## 通用执行规则

* 索引优先，契约优先，必要时再读源码。
* `Me2AI` 默认只读；`AI2AI` 随架构、API、测试、文档树和迭代事实维护。
* 外部契约变化时，同步更新对应 `AI2AI/API` 文档。
* 验证采用最小充分范围，不把全套测试作为代码修改的默认动作。
* 文档、注释、纯展示文案通常只检查格式、链接和结构；除非影响生成流程、配置或构建输入，否则不运行构建。

## 最小充分验证

按影响范围选择验证：

* 单文件或局部实现、无契约变化 → 定向测试、静态检查或受影响模块的最小编译验证。
* 单模块逻辑变化 → 相关模块测试和模块构建。
* 跨模块、API、数据模型变化 → 受影响模块构建，以及必要的契约或集成测试。
* 持久化、协议、基础设施、发布或核心架构变化 → 相关迁移、启动、集成或发布验证。
* 只有影响范围广、项目明确要求，或风险无法局部覆盖时才运行全套测试。

没有独立测试 Agent 的细节任务，由当前 Agent 按最小充分范围完成验证，不因缺少测试 Agent 自动升级为全套测试。

## 迭代任务流程

父 Agent 负责协调、门禁和收口，不独自完成主要实现。

### 1. 读取与定界

读取根索引、必要的局部索引、Spec、API 和架构文档，明确：

* 任务目标和边界。
* 依赖与风险。
* 验收口径。
* 最小充分验证范围。
* 需要更新的 Spec/API/索引。

### 2. 创建任务文档

创建或安排子 Agent 创建迭代任务文档；安排前先判断是否真的需要委派。

任务文档至少明确：

* 目标与范围。
* 关键设计决策。
* Agent 分工。
* 验收标准。
* 测试所有权。
* 验证范围。
* 文档更新项。

创建任务文档时同步在 `AI2AI/索引` 登记任务，状态为 `待开始` 或项目已有等价状态。

不得把任务文档创建和主要代码实现并行。

### 3. 父 Agent 审阅

父 Agent 在实现前审阅：

* 范围。
* 设计决策。
* Agent 分工。
* 验收标准。
* 测试范围。
* 文档更新项。

任务文档未审阅、执行摘要和验证范围未确定前，不启动主要实现。

### 4. 向用户交付执行摘要

任务文档经内部审阅后，父 Agent 必须向用户说明：

* 对目标的理解。
* 关键方案和重要边界。
* 明确不做或暂不处理的内容。
* 预期交付物。
* 真实存在的用户决策项；没有则明确无须额外审批。

用户目标明确、方案无重大分叉且已要求执行时，摘要后继续推进，不机械等待回复。

只有存在以下情况时才进入 `待关键决策` 并暂停相关实现：

* 会显著改变结果的歧义。
* 范围扩大。
* 不可逆操作。
* 兼容性破坏。
* 核心产品/架构分叉。
* 与用户既有决定冲突。

不得只在仓库里创建任务文档而不告诉用户 Agent 将如何执行，也不得把审阅整份内部任务文档的责任转交给用户。

### 5. 分配实现与测试所有权

如果任务文档显式声明 Agent 分工，该分工是强制完成门禁。

* 父 Agent 不得自行替代已声明的设计、实现、测试、验收或其他角色。
* 每个角色必须产生可审阅交付物。
* 缺少任一声明角色交付物时，不得标记 `已完成`。
* 如需改变既有分工，必须先说明原因，并获得用户确认或先更新任务文档。
* 事后补派 Agent 只能作为纠偏记录，不视为原流程合规。

存在独立测试 Agent 时，实现前必须按验收项标明唯一所有者：

* `实现自测`
* `独立验收`

规则：

* 实现 Agent 只写开发所需的最小内部自测，例如新增纯函数、局部算法或编译回归。
* 正式验收测试的设计、实现、执行和证据交付归测试 Agent。
* 测试 Agent 必须从 Spec/验收标准独立推导测试，不以实现 Agent 已写测试作为验收范围来源。
* 测试重点应覆盖外部可观测行为、契约、失败路径、边界和集成装配。
* 同一验收点不得由两个 Agent 各写一套重复测试。
* 测试 Agent 不得仅重跑实现自测后宣称完成独立验收。

如果实现 Agent 已包办主要正式验收测试，父 Agent 应先停止流程并重新划分所有权，而不是通过重复造测试伪造独立性。

### 6. 子 Agent 执行

子 Agent 不是检查清单。请求参数、DTO、Service、Persistence、Controller、排序规则和错误码等关注点，默认属于同一设计/实现任务，除非确有独立交付物和独立验收口径。

只有同时满足以下条件才拆分子 Agent：

* 边界清楚。
* 可独立提交或产出代码/文档/测试。
* 不需与其他 Agent 共同修改同一核心文件。
* 结果可由父 Agent 单独验收。

单接口或单领域闭环默认不超过：

1. 设计 + 实现 Agent。
2. 测试 Agent。
3. 父 Agent 审阅收口。

共享 API、数据模型、持久化、核心 Service 或同一 Controller 的工作优先串行并收敛到同一实现 Agent。

存在 API、数据模型、消息协议、持久化或核心文件依赖的任务必须串行。

并行只用于互不冲突且能实际减少总耗时的工作；若同步和整合成本高于实现成本，应合并。

### 7. 测试与收口

实现完成后，由测试 Agent 按 Spec 独立完成正式验收。

父 Agent只审阅交付物与证据，不重复角色工作：

* 检查测试是否覆盖验收标准。
* 检查命令、环境、结果和失败记录是否完整。
* 检查测试后是否又发生相关变更。
* 覆盖不足时退回原测试 Agent 补测，或重新指派必要范围。

测试完成后没有相关变更时，不得为了保险重复运行相同测试、构建或手动验收。

只有以下情况才允许重新验证，并应限制到受影响范围：

* 测试后代码、配置、依赖或脚本发生变化。
* 证据矛盾或缺失且原角色无法补充。
* 出现新的高风险问题。
* 用户或项目明确要求独立复验。

父 Agent 在收口时修改实现，则相关测试证据立即失效，必须重新交由测试角色验证受影响范围。

### 8. 状态与文档收口

索引状态应跟随真实进度：

* 创建任务 → `待开始`。
* 存在真实用户决策 → `待关键决策`。
* 开始实现/协调实现 → `进行中`。
* 后续按项目状态体系记录，例如 `实现完成待测试`、`测试完成待收口`、`验收待补测`。
* 缺少正式交付物或验证证据时不得提前标记完成。

完成时：

* 填写任务文档完成记录。
* 更新 `AI2AI/索引` 的任务状态和当前迭代进度。
* 如新增、删除、移动或重命名 Spec，同步更新文档树。
* 外部契约变化时更新 `AI2AI/API`。
* 按项目要求提交 git；迭代 commit 使用中文描述。

## 硬性约束

* 不得在任务文档审阅、执行摘要和验证范围确定前启动迭代主要实现。
* 不得把任务文档创建和主要实现并行。
* API、数据模型、协议、持久化或核心文件存在依赖时必须串行。
* 父 Agent 不得替代任务文档中已声明的角色。
* 实现 Agent 不得包办独立测试 Agent 的正式验收测试。
* 测试 Agent 不得仅执行实现 Agent 编写的测试就提交独立验收结论。
* 同一验收点不得为了形式独立重复造测试。
* 父 Agent 不得以收口、保险或复核为名重复仍然有效的正式验证。

## 完成前检查

* 请求类型是否判断正确。
* 是否通过索引读取了必要 Spec/API，避免无目的扫描。
* 是否保持 `Me2AI` 只读，并正确处理 Spec 与实现冲突。
* 契约、测试范围或文档结构变化时是否同步维护 `AI2AI` / `AI2AI/API`。
* 迭代任务是否已有任务文档和用户可见执行摘要。
* 是否只在存在真实关键决策时暂停。
* 已声明 Agent 是否均产生有效交付物。
* 验收项是否具有唯一测试所有者，正式验收是否真正独立。
* 验证是否符合最小充分范围，全套测试是否有明确必要性。
* 任务文档是否有完成记录和有效验证证据。
* `AI2AI/索引` 是否记录最新文档树、任务状态和当前进度。
* 是否按项目要求完成 git commit。
