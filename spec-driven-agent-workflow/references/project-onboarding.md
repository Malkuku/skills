# 仓库初始化与既有项目引入

仅在以下场景读取本文档：

- 用户要在新仓库初始化分层 Spec 工作流。
- 仓库缺少 `Me2AI`、`AI2AI`、索引、API 文档或迭代任务结构。
- 用户要把一个已有 CodeBase 引入该工作流。
- 需要根据已有代码反向构建索引、架构说明、API 文档或初始迭代任务。

## 先判断引入场景

把场景分成三类：

- 新项目初始化：代码很少或尚未开始实现。优先引导用户提供产品需求，再创建 Me2AI 与 AI2AI 骨架。
- 轻量既有项目：已有少量模块，架构边界较清楚。可以快速扫描 CodeBase，反向建立索引、总体架构和关键 API 文档。
- 复杂既有项目：模块多、入口多、历史包袱多或测试缺失。先做引入规划和信息收集，不要一次性承诺完整反向文档化。

## 复杂度评估

先粗略评估：

- 入口数量：应用入口、后台任务、脚本、扩展入口、服务入口。
- 模块数量：核心领域、UI、运行时、存储、共享协议、外部集成。
- 外部契约：公开 API、消息协议、事件协议、数据模型、持久化格式。
- 测试状态：是否有自动化测试、手动验收材料、fixture 或 mock。
- 文档状态：是否已有 README、设计文档、接口说明、路线图或历史任务。
- 风险程度：是否涉及用户数据、持久化迁移、权限、支付、安全、生产系统。

根据复杂度选择策略：

- 小型项目：可以在一个细节任务中创建基础 Spec 骨架。
- 中型项目：建议作为一个迭代任务，先产出引入计划，再补文档。
- 大型项目：拆成多个迭代，先建立索引和总体架构，再逐层补 API 文档和测试方案。

## 新项目初始化流程

1. 询问或整理产品目标、目标用户、核心场景、平台边界和首个可验收版本。
2. 提醒用户先创建 `Me2AI` 产品说明，或在用户授权下根据对话草拟 Me2AI 初稿。
3. 创建 `AI2AI` 骨架：索引、总体架构、测试方案、API 目录、迭代任务目录和模板。
4. 把第一个实现目标拆成迭代任务，而不是直接开始写代码。
5. 先审阅迭代任务文档，再进入实现。

## 既有项目反向构建流程

1. 先读取仓库入口文件和已有文档，识别技术栈、运行入口、模块目录和测试命令。
2. 只在必要时读取源码细节；优先用文件结构、配置文件、导出边界和测试分布判断架构。
3. 反向创建或补全 `AI2AI/索引`，记录当前项目定位、文档入口和代码目录快照。
4. 创建总体架构说明，描述产品边界、运行模型、模块职责和关键约束。
5. 为稳定模块补 API 文档；对不稳定或混乱模块，先标记为待梳理，不伪造确定契约。
6. 创建测试方案，记录现有测试层级、缺口和推荐验证路径。
7. 若需要继续重构或补齐文档，把后续工作拆成迭代任务。

## 需要询问用户的项目细节

不要一次问太多。优先问会影响文档边界和实现方向的问题：

- 这个项目的核心用户价值是什么？
- 当前最重要的运行入口或交付形态是什么？
- 哪些模块/行为已经稳定，哪些还在探索？
- 哪些数据、协议或用户行为必须保持兼容？
- 你希望先文档化现状，还是顺便规划下一轮重构？

如果能从 CodeBase 明确推断，就先推断并标注“根据代码推断”；只向用户询问无法可靠推断、且会影响架构边界的内容。

## 产物建议

最小初始化产物：

- `Spec/Me2AI/核心项目说明.md`
- `Spec/AI2AI/索引.md`
- `Spec/AI2AI/技术选型与总体架构.md`
- `Spec/AI2AI/测试方案.md`
- `Spec/AI2AI/API/README.md`
- `Spec/AI2AI/迭代任务/模板.md`

既有项目可逐步补充：

- 各分层 API 文档。
- 数据模型、事件协议、消息协议或持久化格式文档。
- 当前迭代任务文档。
- 手动验收材料或测试 fixture 说明。

## 注意事项

- 不要为了完整性编造不存在的架构事实。
- 不要把一次反向梳理扩大成隐式重构。
- 不要把历史细节堆进索引；索引只保留入口和当前快照。
- 对复杂项目，优先建立“可导航的地图”，再逐步补契约细节。
